# プラグインの信頼と import の条件

プロジェクトを開くと、プラグインフォルダのコードと、プロジェクトのコードの設定（`loc-studio.config.*`）が動きます。そのため画面のローカルモードは、利用者が確認して信頼するまで、これらのコードを読み込みません。このページは、どのモードで確認が要るか、信頼の確認を通るコードの書き方、個人のプラグインの制限をまとめます。

プラグインを書く人が守ることは、最初の 2 つの節にあります。残りの節は、仕組みの詳細です。

## モードごとの扱い

| 使い方 | project 層と local 層のプラグイン、コードの設定 | import の書き方の検査 |
| --- | --- | --- |
| 画面のローカルモード | 利用者が信頼するまで読み込まない（コードを import しない） | する |
| コマンドライン | 確認なしですべて読み込む | しない |
| Web モード | app 層と project 層を確認なしで読み込む。local 層は読まない | しない |

- 同梱のプラグインと、アプリのフォルダ（app 層。管理者がアプリの隣に置いたもの）のプラグインは、どのモードでも確認なしで読み込みます。
- コマンドラインは、利用者が自分で開くものとして扱い、設定ファイルも確認なしで使います。
- Web モードが確認なしで読み込むのは、プラグインを置いたのがサーバーの管理者だからです。サーバー上のプロジェクトのフォルダに書き込める人は、サーバーでコードを実行できる人です（[WEB-MODE.md の 9 章](../WEB-MODE.md#9-データの保護できないこと確かめていないこと)）。

コマンドラインで動いて画面で動かないプラグインは、信頼していないか、下の import の条件に合っていません。

## 信頼の確認を通る書き方

画面のローカルモードで読み込めるプラグインにするには、次の 3 つを守ります。

1. 読み込むファイルは、文字列で書いた `import` 文、引数が文字列の `import()` と `require()` で指定します。引数を計算する `import(name)` や `require(path.join(...))` は使いません。
2. 相対 import は、プラグインのフォルダ（単一ファイルのプラグインなら、そのファイルのあるフォルダ）の中だけにします。
3. パッケージは、Node の組み込み、`@loc-studio/sdk`、プラグイン自身の `node_modules` にあるものだけを使います。

単一ファイルのプラグインで `eval`、`child_process`、`worker_threads` などを使うと、読み込めません。使うときは、フォルダ形式のプラグインにします（[単一ファイルのプラグインとコードの設定だけで断る書き方](#単一ファイルのプラグインとコードの設定だけで断る書き方)）。

条件に合わないプラグインは、「信頼の確認の条件を満たさないため読み込みません」の読み込みエラーになり、信頼の候補にも出ません。エラーには、ファイル名と行番号、理由が出ます。

```
プラグイン <プロジェクト>/loc-studio-plugins/e-badimport.ts は信頼の確認の条件を満たさないため読み込みません: <プロジェクト>/loc-studio-plugins/e-badimport.ts:1: import "no-such-package-xyz" はプラグインのフォルダの中（node_modules）にありません。信頼の確認では、プラグインのフォルダの外のパッケージは読み込めません
```

この文書群のコードの例は、すべてこの条件を満たします。

## 確認の流れ

プロジェクトの設定ファイル（`loc-studio.project.json`）も確認の対象です。プラグインフォルダの場所は設定ファイルで決まるので、確認は 2 段になることがあります。先に設定ファイルを確認し、信頼するとプロジェクトを開き直して、続けてプラグインを確認します。設定ファイルの確認の中身は、[CONFIG.md の「設定ファイルの確認」](../CONFIG.md#設定ファイルの確認画面のローカルモード)にあります。

- プラグインを書き換えると、ハッシュが変わり、もう一度確認が要ります。
- 信頼していないプラグインの実装を設定が参照していても、プロジェクトは開きます（「登録されていません」の警告になります）。
- コードの設定を信頼していないときは、`loc-studio.project.json` だけで開きます。JSON だけでは設定として足りない場合は、プロジェクトは制限された状態で開き、信頼するまで、確認のダイアログと設定とプラグインの一覧のほかは使えません（[SERVER-API.md の制限された状態](../SERVER-API.md#制限された状態)）。
- あとから信頼するとき、信頼を取り消すときは、上のバーの「プラグイン」のダイアログを使います。

## ハッシュに入るファイル

信頼は、読み込むと実行されうるファイルの中身のハッシュで記録します。ハッシュに入るファイルは、確認のダイアログの「確認の対象のファイル」の一覧で見られます。

| 対象 | ハッシュに入るファイル |
| --- | --- |
| フォルダ形式のプラグイン | フォルダの中のすべてのファイル（`node_modules` を含む）。フォルダの外を指すシンボリックリンクがあると、読み込みエラーになる |
| 単一ファイルのプラグイン | そのファイルと、そこから相対 import でたどれるファイル（推移的に）。どれも、プラグインのファイルがあるフォルダの中にあることが必要 |
| コードの設定 | 単一ファイルのプラグインと同じ規則。基準はプロジェクトのフォルダ |

import した JSON などのファイルも、ハッシュと一覧に入ります。

import をたどるときは、ファイルを構文解析します（`acorn`。TypeScript は、Node の `module.stripTypeScriptTypes` で型を取り除いてから解析します）。import の解決は、実際に読み込むローダー（`jiti`）と同じ手順で行います。たとえば `import "./x"` に対して `x.ts` と `x.js` の両方があるときは、ローダーが読む `x.js` がハッシュに入ります。コメントや文字列の中に `import(x)` のような文字があっても、構文解析で見つけるので断りません。

## 断る書き方

確認のときに、読み込むファイルを前もって決められない書き方は断ります。フォルダ形式でも単一ファイルでも断るのは、次の書き方です。

- 引数が文字列でない `import()` と `require()`（式の入らないテンプレートリテラルは文字列として扱います）
- 値として使う `require`（別の変数に入れるなど）、`require.resolve` 以外の `require` のプロパティ（`require.cache` など）、引数が文字列でない `require.resolve`、`module.require`、`module.constructor`
- `createRequire`、`node:module` の `builtinModules` と `isBuiltin` 以外のメンバー、`require("node:module")`、`import("node:module")`、`node:module` の名前空間の import と既定の import、`node:module` からの再エクスポート、`process.dlopen`。`import { builtinModules, isBuiltin } from "node:module"` のように名前を指定して取り出すのは使えます。`node:` のない `module` も同じ扱いです
- `import.meta.resolve`、`import.meta.glob` の類、`import.meta[式]`
- 構文解析できないファイル

import の指定そのものにも条件があります。

- import できるパッケージは、Node の組み込み、`@loc-studio/sdk`（この名前そのものだけ。`@loc-studio/sdk/…` のような下の階層は不可）、プラグイン自身の `node_modules`（コードの設定ならプロジェクトの `node_modules`）にあるものだけです。
- 絶対パスと URL（`file:`、`data:`、`http:` など）の import、パッケージ名のあとに `..` を含む指定、フォルダの外に出る相対 import は断ります。
- `plugin.json` の `main` は、どのモードでも、プラグインのフォルダの中を指す必要があります。

### 単一ファイルのプラグインとコードの設定だけで断る書き方

単一ファイルのプラグインとコードの設定では、ハッシュに入るのは import でたどれるファイルだけです。そのため、たどれないコードを動かせる次の書き方も断ります（エラーは、フォルダ形式のプラグインにするよう案内します）。

- `eval`（呼び出しに限らず、名前を参照するだけでも）、値として使う `Function`（`new Function`、`Function(...)`、`instanceof Function` も）
- `process.getBuiltinModule`
- `module`、`require`、`process`、`globalThis`、`global`、`window`、`self` への計算したプロパティのアクセス（`process[k]`、`module["exports"]` など）
- `globalThis`、`global`、`window`、`self` の `eval`、`Function`、`require`、`process`、`module`
- アロー関数でない関数の外での `arguments`
- 値として使う `module`（`module.exports` や `module.id` のようなプロパティの参照は使えます）
- 組み込みの `vm`、`worker_threads`、`child_process`、`cluster`、`repl`、`inspector`、`wasi` の読み込み（`import` 文、`import()`、`require`、再エクスポートのどれも。`node:` の有無を問わない）

関数の中で、`eval`、`Function`、`arguments`、`module` と同じ名前のローカル変数や引数を使うのは断りません。

### フォルダ形式のプラグインでの扱い

フォルダ形式のプラグインは、フォルダの中のすべてのファイルがハッシュに入るので、上の追加の書き方は断りません。`eval` や `child_process` を使いたいときは、フォルダ形式のプラグインにします。

その代わり、フォルダの中のコードのファイルすべて（`node_modules` の中も、import されていないファイルも）に、[断る書き方](#断る書き方)の最初の一覧の検査をします。`node_modules` に入れたライブラリが `createRequire`、`require("module")`、引数を計算する `require` などを使っていると、そのプラグインは画面のローカルモードでは読み込めません。その場合の対処は 2 つあります。

- 依存するライブラリごと、フォルダの中の 1 つのファイルにまとめます（バンドルします）。プラグインはフォルダ形式のままにします。単一ファイルのプラグインにすると、バンドルの中の `Function` などで、追加の検査に引っかかることがあります。
- プラグインをアプリのフォルダ（app 層）に置きます。app 層は確認なしで読み込みます。

## 信頼の確認で分かること、分からないこと

この検査はサンドボックスではありません。目的は、正直に書かれたプラグインについて、動くコードのファイルがすべて確認の一覧に出てハッシュに入ることを確かめることです。信頼したコードは、実行時には利用者の権限で何でもできます。

- 確認で守れるのは、読み込む時点で静的にたどれるファイル（フォルダ形式ならフォルダの全ファイル）が、確認したときから変わっていないことだけです。フォルダ形式のプラグインが実行時に `eval` で動かすコードや、どの形でもネットワークから取ってくるものは、ハッシュに入りません。
- ハッシュを計算してから読み込みが終わるまでの間にファイルが書き換えられると、書き換えられたコードが 1 回動きます。読み込みのあとにもう一度ハッシュを計算して比べるので、変わっていれば読み込んだものを捨てて確認待ちに戻しますが、動いたコードがしたことは取り消せません。2 回目の計算の前に元に戻された場合は、気づけません。
- enum や namespace のように、型を取り除くだけでは済まない TypeScript の書き方があるファイルでは、エラーの行番号が少しずれることがあります。

## 個人のプラグインを制限する

個人の設定フォルダ（local 層）の `plugins/` は、その人が自由にコードを置けます。プロジェクト設定の `localSettings.enforce` で、種類ごとに禁止できます。

```json
"localSettings": {
  "enforce": { "plugins.local.formats": "deny", "plugins.local.trees": "deny" }
}
```

`plugins.local.<欄>` の欄は、`trees`、`formats`、`syntaxes`、`sources`、`columns`、`generators`、`actions`、`validators`、`renderers` で、値は `"deny"` です。`plugins.local` を `"deny"` にすると、すべての種類を禁止します。禁止された実装は登録されず、警告（「設定で禁止されているため登録しませんでした」）が出ます。

`enforce` で制限できるのは local 層だけです。コマンドラインは project 層のプラグインを確認なしで読み込むので、プロジェクトのフォルダに書き込める人は、CLI を使う人の環境で任意のコードを実行できるものとして扱ってください。

サンプルプロジェクト（`"plugins.local.formats": "deny"` を設定済み）で、個人のフォルダに置いたフォーマットが、CLI の `plugins` の警告に出て、登録されないことを確かめました。

## 確かめたこと

- 断る書き方と使える書き方は、1 つずつ試すファイルを作って、`packages/core` の `inspectPluginCode` と `scanSource` で確かめました（2026-11-15）。単一ファイルの追加の検査は 24 通りで、フォルダ形式で `eval` と `node:vm` を使うものが読み込めることを含みます。
- 関数の中の `const module = …` が通ること、`import("node:module")`、`node:module` の名前空間と既定の import、再エクスポートがフォルダ形式でも断られること、単一ファイルで `import("node:vm")` と `child_process` / `worker_threads` の再エクスポートが断られることを確かめました。
- `x.ts` と `x.js` が両方あるときに `x.js` がハッシュに入ること、`node_modules` のライブラリの `require("module")` でフォルダ形式のプラグインが断られること、enum のある TypeScript で行番号がずれることを確かめました。
- この文書群のコードの例と、`examples/sample-project`、`examples/remote-project` のプラグインは、サービス層を `pluginTrust: "prompt"` で開き、信頼したあとに、読み込みエラーなしで読み込まれました。
- 画面（ブラウザ）での信頼のダイアログの操作は、確かめていません。説明はコードに基づきます。
